# 데이터 파이프라인 설계 및 구축

## 1. 왜 v2를 만들었는가

v1에서 실제 운영 데이터를 조사하면서, 일부 데이터가 제한되어 있거나 서로 연결되지 않아 사용자 행동을 지속적으로 분석하는 데 한계가 있음을 확인했다.

따라서 v2에서는 **서비스가 계속 운영되며 데이터가 쌓인다는 전제에서, 필요한 데이터를 일관되게 적재하고 반복해서 분석할 수 있는 구조**를 만드는 것을 목표로 했다.

실제 서비스 데이터는 사용자 행동을 확인하는 데 사용하고, 합성 데이터는 데이터가 충분히 쌓인 상황을 가정해 파이프라인과 분석 구조를 검증하는 데 활용했다.

이를 위해 **Raw → Staging → Mart**로 데이터를 단계별로 관리하고, Airflow를 통해 적재와 가공 과정을 반복 실행할 수 있도록 구축했다.

---

## 2. 실제 데이터와 합성 데이터를 함께 사용한 이유

v2에서는 실제 서비스 데이터와 합성 데이터를 함께 사용했다.

두 데이터는 목적이 달랐다.

### 실제 데이터

실제 데이터는 **현재 서비스에서 실제로 발생한 사용자 행동을 확인하기 위한 데이터**다.

웹앱에서 발생한 데이터는 Supabase PostgreSQL에 저장된다.

```text
Next.js / Vercel
      ↓
Supabase PostgreSQL
      ↓
BigQuery Raw
```

현재 실제 데이터 규모는 다음과 같다.

* 사용자 23명
* 질문 24개
* 투표 700건

현재 데이터만으로는 장기간 리텐션이나 다양한 사용자 행동을 분석하기에 규모가 부족했다.

### 합성 데이터

그래서 실제 서비스와 동일한 데이터 구조를 유지하면서 더 많은 사용자가 발생하는 상황을 만들어 파이프라인을 검증했다.

```text
generator/synthetic-v2.yaml
          ↓
      generate.py
          ↓
       CSV 40개
       7.4GB
          ↓
   Local PostgreSQL
          ↓
      BigQuery Raw
```

생성한 데이터는 다음과 같다.

* 사용자 20,000명
* 질문 240개
* 140M+ rows

합성 데이터는 실제 서비스와 동일한 40개 테이블과 컬럼 구조를 사용했다.

따라서 실제 데이터와 합성 데이터에 **같은 적재 과정과 같은 분석 쿼리를 적용할 수 있도록** 구성했다.

즉, 실제 데이터가 충분히 쌓이기 전에는 합성 데이터로 구조를 검증하고, 이후 실제 데이터가 쌓이면 동일한 구조에서 실데이터를 분석할 수 있도록 했다.

합성 데이터는 실제 서비스에 섞이지 않도록 웹앱에서 사용하는 Supabase와 분리했다.

또한 생성한 CSV를 바로 BigQuery에 적재하지 않고 Local PostgreSQL을 거쳤다. 실제 서비스 DB와 동일한 제약조건을 적용한 상태에서 데이터를 먼저 검증하기 위해서다.

17개의 SQL 정합성 검사를 수행하고, 실제 DB와 동일하게 FK / UNIQUE / CHECK 제약조건도 적용했다.

BigQuery에는 이러한 DB 제약조건이 없기 때문에 **잘못된 데이터가 분석 단계까지 들어오기 전에 별도로 검증하는 과정**을 두었다.

## 3. BigQuery Raw: 실제 데이터와 합성 데이터를 같은 구조로 관리

검증이 끝난 실제 데이터와 합성 데이터는 BigQuery의 동일한 Raw 영역에 적재했다.

대신 데이터가 서로 섞이지 않도록 `_source`와 `_loaded_at`을 추가했다.

```text
_source

- supabase : 실제 데이터
- local    : 합성 데이터

_loaded_at

- BigQuery에 적재된 시각
```

### 데이터 출처를 함께 관리한 이유

실제 데이터와 합성 데이터는 각각 독립적으로 생성되기 때문에 ID가 겹칠 수 있다.

예를 들어 실제 질문 ID가 `8`이고 합성 질문 ID도 `8`일 수 있다.

```text
실제 질문 8
합성 질문 8
```

둘은 전혀 다른 데이터지만 `id`만으로 연결하면 잘못된 데이터가 연결될 수 있다.

이런 경우 SQL 오류가 발생하지 않기 때문에 더 주의가 필요했다.

그래서 모든 Staging 조인에서는 ID와 데이터 출처를 함께 사용했다.

```sql
ON a.id = b.id
AND a._source = b._source
```

즉, **ID와 데이터 출처가 모두 같을 때만 같은 데이터로 연결**하도록 했다.

---

## 4. 증분 적재: 새로 바뀐 데이터만 가져오기

데이터가 계속 쌓이는 상황을 고려해 매번 전체 데이터를 다시 적재하지 않고, 지난번 적재 이후 새로 추가되거나 수정된 데이터만 가져오도록 구성했다.

각 테이블의 마지막 적재 시점은 `_load_state`에 기록하고, 다음 적재에서는 해당 시점 이후 변경된 데이터만 가져온다.

이를 통해 데이터가 증가하더라도 매번 전체 데이터를 다시 처리하지 않고 필요한 데이터만 적재할 수 있도록 했다.

## 5. Staging: 분석에 필요한 기준을 정리

Raw에 원본 데이터를 그대로 저장했다면, 다음 단계에서는 분석할 때 반복해서 사용하는 조건과 조인을 정리할 필요가 있었다.

Staging에서는 **여러 분석에서 반복해서 사용하는 데이터와 판단 기준을 미리 정리했다.**

원본 Raw를 직접 수정하지 않고 `CREATE OR REPLACE VIEW`로 관리했다.

처음에는 6개 View로 시작했지만 대시보드를 구성하면서 필요한 데이터를 추가했고, 최종적으로 10개 View를 구성했다.

```text
stg_user
stg_question
stg_vote
stg_vote_session
stg_vote_received
stg_friend_edge
stg_report
...
```

### 친구 관계

친구 관계는 한 관계가 양쪽 사용자 기준으로 저장되어 있었다.

따라서 분석할 때 같은 친구 관계를 두 번 세지 않도록 기준을 정했다.

`stg_friend_edge`에서는 원본의

```text
user_low_id < user_high_id
```

기준을 이용해 하나의 친구 관계를 하나의 데이터로 관리했다.

### 투표자 정보

`voter_id`는 일반 사용자 분석 데이터에 직접 포함하지 않았다.

누가 나에게 투표했는지는 하트 구매를 통해 확인할 수 있는 정보이기 때문에 일반적인 사용자 분석과 분리했다.

필요한 경우에만 사용할 수 있도록 별도 View로 만들었으며, 대시보드에서는 사용하지 않았다.

### 매출 기준

MVP의 충전 버튼에는 실제 결제가 아닌 테스트 거래도 포함되어 있었다.

따라서 모든 거래를 매출로 계산하면 실제 매출과 테스트 거래가 섞인다.

이를 구분하기 위해 Staging에서 다음 기준을 정리했다.

```text
is_stub
is_success
is_revenue
```

**성공한 거래이면서 테스트 거래가 아닌 경우만 실제 매출**로 집계하도록 기준을 통일했다.

이처럼 여러 분석에서 반복해서 사용하는 판단 기준은 Staging에서 한 번 정의하고 이후 단계에서 동일하게 사용하도록 했다.

## 6. Mart: 대시보드에서 바로 사용하는 데이터

Staging에서 분석 기준을 정리한 뒤, 대시보드에서 반복해서 사용할 데이터를 Mart로 구성했다.

Mart는 최종적으로 Looker Studio 대시보드에서 사용하는 분석용 테이블이다.

최종적으로 8개 Mart를 구성했다.

```text
mart_user
mart_user_activity
mart_daily
mart_funnel_step
mart_distribution
mart_report
mart_heart_flow
mart_backlog_weekly
```

처음에는 월별 집계를 중심으로 설계했다.

하지만 대시보드에서 주간 필터와 전주 비교가 필요해지면서 월별로 미리 집계한 데이터만으로는 원하는 분석을 다시 만들기 어려웠다.

그래서 Mart는 다음 기준으로 다시 설계했다.

* 모든 Mart에 날짜 기준 포함
* 비율보다 분자와 분모를 저장
* DISTINCT 결과를 지나치게 미리 집계하지 않음
* 퍼널과 분포는 이벤트 날짜 또는 코호트 날짜를 기준으로 조회

### 조회 비용 감소 전략

Raw에는 대용량의 원본 데이터가 들어 있다.

합성 데이터에서 가장 큰 `vote_candidate` 테이블은 약 4.9 GiB였다.

이 데이터를 대시보드의 여러 차트가 반복해서 조회하면 불필요하게 많은 데이터를 읽게 된다.

그래서 대시보드에서 자주 사용하는 데이터는 Mart에서 미리 집계해 **대시보드가 읽어야 하는 데이터 양을 줄였다.**

2026-08-18 기준 Mart는 약 495 MiB였다.

## 7. Airflow: 전체 과정을 자동화

앞에서 구성한 Raw → Staging → Mart 과정을 데이터가 추가될 때마다 직접 실행하지 않도록 Airflow로 자동화했다.

전체 과정은 두 개의 DAG로 나누었다.

```text
① Raw 데이터 적재

ping_raw_load

├─ extract_load.py
└─ verify_load.py

        ↓

Raw 적재 및 검증

        ↓

② 분석용 데이터 생성

ping_mart_build

├─ quality_check.py
└─ build.py --layer mart

        ↓

Mart 생성
```

첫 번째 DAG에서 Raw 데이터를 적재하고 데이터 품질을 확인한다.

검증을 통과한 경우에만 두 번째 DAG가 실행되어 Mart를 새로 만든다.

Raw 적재가 실패하거나 데이터 품질 검사를 통과하지 못하면 Mart를 새로 만들지 않는다.

이를 통해 **데이터 적재부터 분석용 데이터 생성까지의 과정을 하나의 반복 가능한 흐름으로 구성했다.**

## 8. 최종 구조

전체 구조는 다음과 같다.

```text
[실제 데이터]

웹앱
Next.js / Vercel
      ↓
Supabase PostgreSQL
      ↓
                       ┌────────────────────┐
[합성 데이터] ────────→│ BigQuery Raw       │
generate.py            │ 40 tables          │
      ↓                │ 124M+ rows         │
Local PostgreSQL ─────→│ 8.74 GiB           │
                       └─────────┬──────────┘
                                 ↓
                         Staging 10 Views
                                 ↓
                          Mart 8 Tables
                                 ↓
                         Looker Studio
                                 ↓
                     주간 리포트 / 대시보드
```

```text
실제 데이터 ─┐
             ├→ Raw → Staging → Mart → Dashboard
합성 데이터 ─┘
```

v1에서는 실제 운영 데이터를 통해 서비스의 이용 현황과 이탈 패턴을 확인했지만, 데이터가 제한되어 있어 사용자 행동을 연결하거나 같은 분석을 지속적으로 반복하는 데 한계가 있었다.

v2에서는 이러한 한계를 바탕으로 **서비스가 계속 운영되고 데이터가 쌓이는 상황을 가정한 데이터 구조와 파이프라인을 구축했다.**

실제 데이터와 합성 데이터를 같은 구조로 관리하고, 원본 데이터 적재부터 분석용 데이터 생성까지의 과정을 자동화했다.

그 결과 새로운 데이터가 추가되더라도 기존 구조를 그대로 활용해 **같은 분석을 반복하고 이전 데이터와 비교할 수 있는 기반**을 마련했다.

이번 프로젝트에서는 특정 분석 결과를 도출하는 것에서 나아가, **실제 데이터 조사에서 발견한 한계를 데이터 구조와 파이프라인 설계로 연결해본 경험**을 얻었다.

향후 실제 데이터가 충분히 쌓이면 사용자 세그먼트별 행동 차이를 비교하고, v1에서 확인하기 어려웠던 이탈 원인에 대한 가설을 실제 데이터로 검증할 계획이다.
